# ADR-001: ESPHome/MQTT 브릿지에서 라즈베리파이 RS-485 유선 직접 제어 파이썬 데몬으로의 피벗

## 1. 콘텍스트 (Context)
초기 설계에서는 ESP32 칩에 ESPHome 펌웨어를 올리고 Wi-Fi 무선 통신을 거쳐 MQTT 브로커를 활용하는 다단계 무선 브릿지 아키텍처를 계획하였습니다. 
그러나 실제 산업 및 상용 에어컨 제어 환경을 정밀하게 재분토한 결과 아래와 같은 치명적인 한계점이 노출되었습니다:
1. **무선 인프라 불안정성**: 철골 구조물과 실외기실의 밀폐 구조 특성상 Wi-Fi 도달률이 떨어져 통신 손실 가능성이 큼.
2. **다중 장애 지점(SPOF)**: ESP32 하드웨어 고장, 공유기 중단, MQTT 브로커 크래시 등 제어 채널 내 거쳐 가야 할 중개 프로세스가 너무 많음.
3. **유지보수 코스트**: ESP32의 C++ 소스 빌드 및 OTA 업데이트, 펌웨어 관리 코스트가 중복 발생함.

따라서, 이 모든 중개 레이어를 걷어내고 실외기 PCB에 있는 RS-485 통신 단자(CENA, CENB)에 안정적인 절연 컨버터를 이용해 라즈베리파이를 유선으로 직결하기로 결정하였습니다.

## 2. 아키텍처 결정 (Decision)
- **결정 사항**: 무선 게이트웨이 및 MQTT 중개 구조를 완전히 전면 폐기하고, 라즈베리파이(Linux) 환경에서 `pyserial`을 사용하여 LGAP 바이너리 프로토콜을 밑바닥부터 직접 파싱 및 폴링 제어하는 **단독 파이썬 데몬(python-raw-lgap-daemon)**을 구축한다.

## 3. 대안 분석 및 비교

| 비교 지표 | 대안 A: ESPHome + MQTT (기존) | 대안 B: Python Raw RS-485 직접 제어 (결정) |
| :--- | :--- | :--- |
| **물리적 안정성** | ⚠️ 낮음 (Wi-Fi 무선 간섭 및 패킷 손실) |  **매우 높음** (100% 산업용 유선 노이즈 차단 배선) |
| **시스템 복잡도** | ⚠️ 높음 (ESP32 펌웨어 + MQTT 브로커 필요) |  **낮음** (라즈베리파이-컨버터-실외기 단순 직결) |
| **구현 난이도** |  낮음 (esphome-lgap 오픈소스 활용) | ⚠️ 높음 (바이너리 체크섬 및 폴링 엔진 자체 구현) |
| **장애 조치 편의성**| ⚠️ 까다로움 (원격 하드웨어 리셋 곤란) |  **매우 쉬움** (systemd로 프로세스 자동 리스타트 가능) |
| **PoC 실효성** | 중간 (프로토타입 작동 증명 수준) |  **매우 우수** (실제 빌딩 제어 시스템과 호환 규격 입증) |

## 4. 결과 및 트레이드 오프 (Consequences)

### 긍정적 측면 (Pros)
- 무선 네트워킹 불안정이 완전히 제거되어 유선 레벨의 패킷 신뢰성 확보.
- 관리 대상 장비가 라즈베리파이 1대로 한정되어 상용 배포 및 운영 유지보수가 극도로 단순해짐.
- ESPHome의 제한된 기능에 가둘 필요 없이 파이썬의 강력한 기능을 활용해 프로토콜 고도화 및 커스텀 비즈니스 로직 작성 용이.

### 부정적 측면 (Cons)
- C++ ESPHome 라이브러리가 뒤에서 대신 처리해 주던 **'바이너리 바이트 처리, XOR 체크섬 검증, 반이중 시간차 제어'**를 파이썬 소프트웨어 코드 레이어에서 완전히 제로 베이스로 정밀하게 구현해야 하는 기술적 부하 발생.
- 실외기 PCB 단자까지 직접 배선해야 하므로 실 시공 노력이 발생함 (팀 내 장비 전문가가 동반되므로 소프트웨어 팀 리스크는 제한적임).
